# 規劃：多專案 / 多團隊（TestWeaver v1.1）

> 狀態：**規劃中**（尚未實作）。目標版本：v1.1。相關 Roadmap 見 `README.md`。

## 0. 目標 vs 非目標
- **目標**：一個平台可容納**多個團隊（team）**；每個團隊有自己的專案、成員與**團隊級角色**；資料依團隊**隔離**（用戶只看得見自己團隊的專案/計畫/缺陷）；保留全域 **platform admin** 做跨團隊管理。
- **非目標（這期不做）**：計費/限額、跨團隊共用專案、SSO/OIDC 連線、細粒度欄位級權限。

## 1. 現況 gap（基於 v1.0.0）
| 概念 | 現況 | 缺口 |
| --- | --- | --- |
| 多專案 | ✅ `Project` 已存在（UI 有專案選擇器） | 已可用；只是**全域可見**（無團隊隔離） |
| 團隊 | ❌ 無 `Team` 概念 | 需新增 team + 成員 |
| 專案歸屬 | `Project.owner_id`（可空、未用） | 改為 `project.team_id`（FK team） |
| 角色 | 全域 `User.role`（admin/qa_lead/tester）→ 控制選單 | 需**團隊級角色**（每個 membership 一個 role）＋保留 platform admin |
| 資料隔離 | ❌ 任一用戶可見所有專案 | 所有 list/get 需按「所在團隊」過濾 |

> 結論：**多專案已在**，真正的增量是 **多團隊（tenancy）+ 團隊級 RBAC + 資料隔離**。

## 2. 資料模型變更
**新增表**
- `team`：`id, name, description, created_at`
- `team_member`：`id, team_id(FK), user_id(FK), role, created_at`；`UNIQUE(team_id, user_id)`
  - `role ∈ { owner, qa_lead, tester }`（團隊級）

**改動**
- `project`：加 `team_id (FK team.id, NOT NULL)`（backfill 後）。
- `user`：保留 `role`，**重新定義語意**——`role='admin'` = **platform admin**（跨團隊）；其他人靠 `team_member.role` 決定權限。
- 下游（spec/test_item/plan/case/defect/revision/report）**不加 team 欄位**——team 經 `project → plan` 繼承，避免重複與不一致。
- （選用）`audit_log.team_id`：跨團隊稽核更好追溯。

## 3. 授權模型
- **Platform admin**（`user.role='admin'`）：管理團隊/成員、看全部資料、`/platform`＋稽核。可同時是某個 team 的 member（建議）。
- **Team roles**（`team_member.role`）：

  | 能做什麼 | owner | qa_lead | tester |
  | --- | :-: | :-: | :-: |
  | 看本團隊專案/計畫/缺陷/報表 | ✅ | ✅ | ✅ |
  | 建專案/計畫/執行/自測 | ✅ | ✅ | ✅ |
  | 成員與角色管理（本團隊） | ✅ | — | — |
  | 刪除專案 / 高風險操作 | ✅ | —（可配） | — |

- **選單**：由「platform admin? + 所在團隊角色」共同決定（延伸現有 `allowedPathsForRole` → `allowedPathsForUser(user, teamRole)`）。
- **資料隔離（關鍵，Service 層強制）**：所有查詢先解析「當前團隊」→ 該用戶在該 team 的 membership；無權 → 404/403。前端只是配合隱藏，**安全邊界在後端**。

## 4. API 變更
**新增（`/teams`，team owner / platform admin）**
- `GET /teams`、`POST /teams`、`GET /teams/{id}`、`PATCH /teams/{id}`
- `GET/POST /teams/{id}/members`、`PATCH /teams/{id}/members/{user_id}`（改角色）、`DELETE .../members/{user_id}`
- `GET /me/teams`（我所在的團隊）＋「切換目前團隊」

**改動（既有端點加 team scoping，簽名不變、行為變）**
- `/projects`、`/test-plans/*`、`/defects`、`/reports/*`… 全依「當前團隊」過濾（由 token→membership 解析）。
- team 標識：header `X-Team` ＋ session 預設（缺省＝首個團隊）。

## 5. 前端變更
- **Team switcher**：Header/Sider 頂部加「目前團隊」下拉（`/me/teams`），切換後所有頁籤資料重載。
- **Scoped 資料**：各頁面讀取帶當前 team。
- **團隊設定**（owner / platform admin）：成員 Table（加人/改角色/移除）——延伸現有 `SettingsPage` 或新增「團隊」頁。
- **角色選單**：改吃「team role」（現 `roles.ts` 的邏輯升級）。

## 6. 遷移與相容（**non-breaking**）
1. 新 migration `0010_multi_team`：建 `team`、`team_member`；`project.team_id`（先 nullable→backfill→NOT NULL）。
2. **Default team**：建「預設團隊」；每個既有 `project` → 該 team；每個既有 `user` → 成為 member（全域 role 映射為 team role：admin→owner、qa_lead→qa_lead、tester→tester）。
3. 單團隊場景下**行為不變**（所有舊資料都在 default team，舊用戶仍看得到）→ 平滑升級。
4. `ensure_default_admin` 補：platform admin 也加入 default team（owner）。

## 7. 分階段實施
- **T1（資料層 + 隔離）**：team/member 模型＋migration＋default team backfill；`/me/teams`＋現有端點加 team scoping（先支援單一 default team，驗證不回歸）。
- **T2（團隊級 RBAC + 管理 UI）**：team CRUD＋memberships API；team role 授權；前端 team switcher＋團隊成員設定頁；選單吃 team role。
- **T3（platform admin + 打磨）**：platform admin 跨團隊管理、稽核加 team_id、切換團隊 UX、邊界（空團隊/最後一個 owner 保護，比照現有「最後一個 admin」邏輯）。

## 8. 測試策略
- Service：membership→可見範圍（A 團隊用戶讀 B 團隊專案 → 404）。
- API：每角色×跨團隊授權矩陣；最後一個 owner 保護。
- 遷移：seed 舊資料 → 跑 migration → 斷言全進 default team、role 映射正確。
- 前端：team switcher、選單隨 role 變、成員表 CRUD（vitest/RTL）。

## 9. 風險 / 開放問題
1. **邀請流程**：先做「owner 直接加既有用戶（by username）」；email 邀請（需 mail）留後。
2. **platform admin 是否必須也是 member** 才能操作該 team？（建議：admin 可 override，但稽核要標記）
3. **team_id 傳法**：header vs query——建議 header `X-Team`＋session 記憶。
4. **刪除 team**：僅 platform admin；team 下有專案時禁止/需確認（軟刪或 cascade 策略）。
5. **既有 `Project.owner_id`**：廢棄或保留為「團隊內專案負責人」？（建議保留語意＝負責人）
